## Context

ADR-007 defines two separate authentication boundaries and explicitly does not provide a shared boundary by default. Platform operators authenticate against platform-owned identities in central storage; platform authentication belongs to the Back Office boundary (ADR-002), runs in central context, and Back Office entry must not require tenant resolution. Tenant users authenticate against tenant-owned identities in the tenant identity store selected by the resolved tenant context (ADR-003, ADR-006), and tenant resolution must complete before tenant-user authentication is evaluated.

The runtime already resolves tenant context in `App\Tenant\*` via `TenantSubscriber` at kernel.request priority 20, which runs before the Symfony firewall (priority 8). Upstream changes are assumed delivered: `identity-model` provides platform-operator and tenant-user identity records; `tenant-database-connectivity` provides selection of the tenant identity store from the resolved tenant context; `tenant-boundary-enforcement` provides the fail-closed tenant route boundary and classification of routes as tenant-facing vs Back Office / central.

This change wires Symfony Security so each boundary has its own firewall, user provider, and authentication state, with tenant authentication strictly tenant-context-first and fail-closed, and with no silent fallback between the central and tenant identity stores in either direction. It defines authentication behavior only; authorization, MFA, credential mechanics, and login UX are out of scope per ADR-007.

## Goals / Non-Goals

**Goals:**
- Provide a central platform-authentication firewall for Back Office (`/bo`) that authenticates platform operators against the central platform-owned identity store and requires no tenant resolution to enter.
- Provide a tenant-authentication firewall for tenant-facing routes that authenticates tenant users only after tenant resolution, against the tenant identity store selected by the resolved tenant context.
- Enforce tenant-context-first ordering: the tenant authenticator must not inspect or query any tenant identity store, credential, session, or tenant authentication state until tenant context is resolved and the tenant is eligible for tenant-facing access.
- Fail closed for tenant authentication whenever tenant context is missing, unresolved, inactive, suspended, archived, deleted, ambiguous, or unavailable.
- Forbid silent fallback between central and tenant identity stores in both directions.
- Scope and isolate authentication state per boundary; bind tenant authentication state to one resolved tenant and reject it on mismatch or tenant ineligibility; prevent any privilege crossover between boundaries; ensure matching identity attributes never imply authentication elsewhere.

**Non-Goals:**
- Roles, permissions, and authorization policies (RBAC/ABAC, capability models) — authorization is a separate concern (ADR-007).
- MFA, password complexity/reset workflows, credential/authenticator mechanics, OIDC/SAML/LDAP, identity federation, login-page UX, and concrete tenant-facing URL topology.
- Session storage implementation details, support impersonation, cross-boundary account switching, service accounts, and tenant directory synchronization (deferred to later ADRs).
- Defining identity records or tenant identity-store selection (owned by `identity-model` and `tenant-database-connectivity`); this change consumes them.
- Changing tenant resolution (`TenantSubscriber`/`TenantResolver`) or the route boundary (`tenant-boundary-enforcement`).

## Decisions

- **Two separate firewalls, never a shared one.** Configure two Symfony Security firewalls in `security.yaml`: a `platform` firewall matched to the Back Office path (`/bo`) running in central context, and a `tenant` firewall matched to tenant-facing routes. ADR-007 forbids a default shared boundary, so there is no firewall or authenticator that authenticates a person first and selects a context later. Alternative considered: a single firewall with a context-selecting user provider — rejected because it reintroduces the shared-boundary model ADR-007 explicitly excludes and risks silent cross-store fallback.
- **Boundary-specific user providers, no cross-store reach.** The `platform` firewall uses a user provider bound exclusively to the central platform-owned identity store; the `tenant` firewall uses a user provider that resolves the tenant identity store from the resolved tenant context. Neither provider can read the other boundary's store. Failed authentication in one firewall does not chain into the other. This directly satisfies the no-silent-fallback invariant in both directions.
- **Tenant-context-first ordering is structural, not advisory.** `TenantSubscriber` (prio 20) already runs before the firewall (prio 8). The tenant user provider/authenticator obtains its identity store strictly through the resolved `TenantContext`; if no eligible tenant context is present it raises a fail-closed authentication failure without touching any identity store. Because store selection is a hard dependency on the resolved context, there is no code path that queries a tenant identity store before resolution. Alternative considered: resolve a default/last-known tenant when context is absent — rejected; ADR-007 forbids default/stale tenant and central-store fallback.
- **Fail closed covers every bad-context case without store inspection.** Missing, unresolved, inactive, suspended, archived, deleted, ambiguous, and unavailable tenant context each cause tenant authentication to deny before any tenant identity store, credential, or tenant authentication state is inspected. Eligibility reuses the tenant lifecycle/eligibility signal from tenant resolution and `tenant-boundary-enforcement` rather than re-deriving it.
- **Tenant authentication state is bound to one resolved tenant.** Tenant authentication state (session/token) records the tenant identifier of the tenant context for which the user authenticated. On every request the bound tenant is compared to the currently resolved tenant context; a mismatch rejects the state. This prevents a tenant session from being replayed against another tenant and keeps tenant state from granting Back Office access. Alternative considered: a single global session pool keyed only by user — rejected because it cannot enforce per-tenant scoping.
- **Eligibility is re-checked on use, not only at login.** Existing tenant authentication state is rejected when the bound tenant is no longer eligible for tenant-facing access (suspended/archived/deleted/inactive/unavailable), per ADR-007. Eligibility is evaluated when establishing state and when using existing state.
- **Isolated state stores per boundary.** Platform and tenant authentication state are isolated (e.g. distinct firewall contexts / session bags / cookie scope) so platform state cannot grant tenant-user identity or ordinary tenant-facing access and tenant state cannot grant Back Office access. Symfony's per-firewall security tokens give this isolation when the firewalls do not share a security context.
- **Matching identity attributes are never proof across boundaries or tenants.** Because store selection is boundary- and tenant-scoped and there is no cross-store lookup, an email or attribute that matches in another boundary or tenant is never consulted; authentication is always evaluated only against the store selected for the current boundary and resolved tenant.

## Risks / Trade-offs

- [A shared or fallback-capable user provider could silently authenticate against the wrong store] → Use two firewalls with boundary-bound providers; the tenant provider only ever resolves the store from the resolved tenant context, and neither provider can read the other store.
- [Tenant authenticator could query the tenant store before tenant resolution] → Make tenant store selection a hard dependency on the resolved `TenantContext`; absence of an eligible context fails closed before any store access (consistent with `TenantSubscriber` prio 20 before firewall prio 8).
- [A tenant session could be replayed against a different tenant] → Bind tenant authentication state to the resolved tenant identifier and reject on mismatch with the currently resolved context.
- [Existing tenant sessions could outlive tenant eligibility] → Re-check tenant lifecycle eligibility on use of existing tenant authentication state, not only at login.
- [Platform and tenant state could bleed into one another] → Keep firewall security contexts and session/cookie scope isolated per boundary so neither token grants the other boundary's access.
- [Back Office entry could accidentally couple to tenant resolution] → Match the platform firewall to `/bo` in central context with no tenant-resolution dependency; tenant resolution failures must never block or alter Back Office authentication.
- [Stale or ambiguous resolution could be treated as a usable tenant] → Treat unresolved, ambiguous, and unavailable context identically to missing context: fail closed, never select a default/stale tenant or the central store.
